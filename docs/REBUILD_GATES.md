## 保存時的去機密邊界

可保存：新寫的通用程式、純合成 fixtures、去機密的測試結果、此草稿，以及上列來源 commit／archive hash。

不可直接複製：實際帳號、機器／使用者路徑、對話與訊息、服務專案與檔案識別碼、原始工具回應、待辦／排隊任務資料、登入資料、權杖、Cookie 或其他個資。原始本地證據與交接檔可能含此類內容，不能因為檔案在工作區就視為可發布。保存候選必須逐檔去機密，測試只保留明確合成的 placeholder。

原封存仍不可讀；本草稿不授權重新下載、改道讀取、建立憑證、擴張權限或部署。

## 重建與整合門檻

| Gate | 可獨立做的純合成工作 | 真實整合尚需的證據 | 目前界線 |
|---|---|---|---|
| Atomic claim | 在新候選的本地儲存層測試同一 generation 的競爭領取、單一勝出與失敗者無副作用。 | 原版或新整合的權威 claim 狀態、所有權及交易語意。 | 可新作；原 provider claim 契約未驗證。 |
| Lease | 定義本地租約取得／續租規則、授權者與失敗行為，測試重啟與競爭條件。 | 實際租約來源、有效狀態與可核對的伺服器語意。 | 原租約長度與規則未知；不能用測試預設值補成原版。 |
| Expiry | 用合成時鐘測試期限前、恰好到期與期限後；明訂邊界及時鐘來源。 | 原契約的期限單位、時鐘信任與目前有效性。 | 已知舊 turn 可被 baseline 排除；這不等同 TTL 驗證。 |
| Lease fencing | 為每次有效重新領取產生較新的 fencing generation；舊 worker 即使恢復，也不能寫入結果或建立新副作用。 | 受保護的實際寫入端確實檢查 fencing 值，並拒絕舊持有者。 | 可在自行控制的儲存層新作；不能宣稱外部提供者也有 fencing。 |
| Cancel | 定義取消的原子轉移、取消與完成競爭、確認回條及失敗恢復；禁止舊取消覆寫新 generation。 | 權威取消狀態及 acknowledgement；已發生的外部副作用如何處理。 | 現有工具可拒絕明示 cancelled／error 的 turn；不能據此證明後端 task 已取消。 |
| Result ingestion 與 exactly-once | 在新候選儲存層以 task、generation、claim、結果身分與結果 hash 做唯一性／交易檢查。同一結果重入應穩定；同一身分的衝突內容應拒絕。 | 實際 durable ingest commit、失敗／重啟恢復、並行回傳及下游副作用的去重證據。 | 靜態解析器對重複快照穩定，不是持久 exactly-once ingestion。 |
| Durable outbox | 結果狀態與待回傳事件在同一筆本地交易提交；重啟後不遺失事件，以固定事件身分重試並保留可核對的 ack。 | 真實目的端的 idempotency／去重與 acknowledgement 契約；不確定結果的查證方式。 | 可新作本地 outbox；沒有目的端契約時，不能保證跨網路 exactly-once delivery。 |
| 完整 Chat 正文 | 測試 final assistant body、明示省略／參照／空正文、錯 task／nonce／方向及矛盾身分的拒收。 | 由受支援工具取得實際完整最終正文與來源身分。 | Preview、摘要、面板、queued、預期答案或手算都不能補正文。 |
| Work binding | 對正式 ID、暫存 ID、相同完整 prompt／nonce 的歷史關聯與錯目標建立合成正反例。 | 可追溯的正式任務 binding 與實際 host mode 證據。 | 相同 prompt／nonce 可支持有限歷史內容關聯；不能自行改寫暫存回條成 provider mapping。 |
| Actual model | 分開保存 requested model、支援能力、inherit policy 與 observed model；測試未知值保持未知。 | 由提供者／實際執行工具回傳的路由或模型中繼資料。 | 不支援逐次選模時應明示沿用對話／任務預設；模型自述與請求值不是實際路由證據。 |
| End-to-end 回傳 | 以合成 receiver／outbox／ingest 模型測試 task、nonce、generation、sender／target 方向與終端回傳狀態。 | 真實受授權目的端的接單、實際執行、完整結果，以及 DOT 端可追溯的取得／ack 證據。 | 工具拉取歷史結果、接收端主動 callback、以及完整私人 bridge 驗收是不同層級，不能合併標成功。 |

### exactly-once 的宣稱限制

新候選可以在明訂的單一交易邊界內測試「同一結果只提交一次」。若另有 outbox、網路與第三方接收端，必須分別證明事件不遺失、重送可辨識、目的端去重及 acknowledgement 語意。只有本地唯一鍵或重跑函式得到相同輸出，不能推出跨系統 exactly-once。無官方目的端契約時，應保留「可能重複／結果不明」狀態與唯讀查證流程，不能把自動重送當成已知安全。

### 真實 e2e 測試的最低要求

1. 測試內容完全合成，不含私人資料、外部新收件人或未授權副作用；測試前先核對既有任務，避免重送。
2. 預期結果不能已在受測 prompt 中完整揭露；驗證器可以獨立檢查答案，但不可用本地產生的答案冒充接收端回傳。
3. 保存真實派送、權威接收端、完整最終正文及 DOT 端取得結果的分層證據；不能只保存聲稱 receiver／model 的模型文字。
4. 對時效、claim、取消、fence 與 generation 的判斷必須來自被採用契約和權威目前狀態；無法取得時明示未驗證。
5. 分別報告內容關聯、正式 binding、實際模式／模型、執行、結果 ingestion、拉取回傳與 push callback。任何層級未知，不能標成完整橋接驗收。

## 後續作品與版本標示

- 保存版：標示為「新增證據工具與重建規格」，附原來源 commit／archive hash 線索；不聲稱包含原 source bytes。
- 重建候選：使用新的候選版本、自己可讀且可測的規格與 schema。每一項 lifecycle／outbox 能力都需實作及驗證後才能從「待實作」改為「已驗」。
- 原版對照：只有取得可讀原來源及原 36／12 項測試後，才開始比對相容性、隔離保存未提交改動並重跑原驗收。不能用新增 90 項測試填補這一步。
- 真實整合：需要官方支援的通道、既有授權及上述證據；新增部署或其他風險須另行確認。此草稿不授權任何遠端動作。

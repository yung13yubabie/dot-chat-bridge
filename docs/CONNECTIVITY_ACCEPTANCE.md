# Single-message acceptance and next boundary

The previously paused canary proposal was superseded by explicit authorization
for one real Chat message and a coordinated browser read. That single test has
completed; [LIVE_ACCEPTANCE.md](LIVE_ACCEPTANCE.md) records the scoped PASS.
This file is not permission to send another message.

The completed scope was native DOT send, Chat execution and complete UI
pull-return to parent DOT. The source is a parent-relayed browser-worker report.
The formal assistant message UUID was not independently visible. No automatic
callback, native full-body reader or database ingestion is certified.

Future acceptance must distinguish these independent gates:

1. Supported full assistant-body retrieval with source identity, fresh task/nonce,
   correct DOT/Chat direction and completed state. Omitted, referenced, truncated,
   paginated or ambiguous content must block acceptance, never use snippets.
2. A real host tool binding with durable dispatch uncertainty and bounded reads;
   unknown send outcomes must be reconciled, never automatically resent.
3. An explicitly identified authorized DOT sink with actual attempt/ACK identity,
   claim/TTL/nonce enforcement and independent read-back of one result/effect.
4. A duplicate return with no second effect, only in a separately authorized
   sink test. The completed test did not exercise this gate.

Current minimum wiring and permission requirements are in LIVE_ACCEPTANCE.md.
Do not create credentials, persistent browser access, a service or deployment
without the concrete required approval. Do not mutate the original probe or
candidate database while diagnosing the reader or preserving evidence.
